# Budget the frame before the flourish

A web UI can be rich and fast at once. The way to do it is to choose effects by **which rendering stage they cost**, not by how impressive they look. Changes to `transform` and `opacity` (and, on current engines, `filter` and `clip-path`) can run on the compositor thread and stay smooth even when JavaScript is busy. Changes to geometry, shadows, gradients, large blurs, global CSS variables or React state redo layout or paint on the main thread every frame, inside a budget of about **10 ms at 60 Hz and about 8 ms for the whole frame at 120 Hz**. Ambitious pages rarely get slow from one bad effect. They get slow because several effects that are each fine add up. Main-thread animation competes with hydration and scroll handlers. Most of the real damage happens at load time, from hero media, font stacks, render-blocking scripts and animation libraries. The page is also built on a fast 60 Hz laptop and judged by a phone that runs the same JavaScript **3–6× slower**. Developers end up trading performance for a mediocre UI because they find the cost after the design is done, and at that point the only fix the budget process offers is deletion. Nearly every costly effect has a cheap twin that looks about the same. In 2026 the platform supplies most of them at 0 KB: View Transitions, `@starting-style`, scroll-driven animations, `content-visibility`, `fetchpriority`, AVIF and WOFF2. The owner's preferred portfolio shows the pattern clearly. Its motion is already the cheap kind. Its two real costs are loading costs: **123 KB of render-blocking compiler JavaScript** from Tailwind's Play CDN, and **74 KB of optical-size font axis**. Fixing both changes nothing a visitor can see. The skill should therefore design performance in, through a fixed build order, a numeric budget and a lint/probe that catches the expensive patterns before a human ever sees the page.

Evidence tags: **[M]** a measurement (profiler, field or lab data) by a third party; **[M-here]** measured first-hand in this repo on 2026-10-29; **[C]** arithmetic from a stated formula; **[V]** a vendor's claim about its own product, or a study commissioned by a vendor; **[G]** a guideline or support fact from a browser vendor, standards body, MDN or webstatus.dev; **[O]** a practitioner's opinion (including vendor authors writing about the platform in general); **[I]** this report's own inference. Many canonical rules in this area are guidelines derived from the pipeline model rather than measurements on current hardware, and the tags say so.

## Every frame gets 8–16 ms, and the stage you touch decides who pays

The browser turns each visual change into up to five stages: JavaScript (or CSS animations, transitions and WAAPI), Style, Layout, Paint and Composite. Displays refresh about 60 times a second, which gives **16.7 ms per frame**. Browser overhead leaves about **10 ms** for your own work, and missing that deadline drops a frame **[G]** ([web.dev](https://web.dev/articles/rendering-performance)). At 120 fps the whole frame is about **8 ms** **[G]** ([Motion docs](https://motion.dev/docs/performance)). This matters because ProMotion iPhones and 120 Hz Android phones are common. Per-frame Style, Layout or Paint work there has roughly half the headroom it has on a 60 Hz desktop monitor, so "smooth on my laptop" proves nothing **[I]**. Discrete interactions work on a longer clock: about 100 ms feels instant, and INP counts as "good" at **200 ms or less** **[G]** ([web.dev](https://web.dev/articles/rendering-performance); [web.dev INP](https://web.dev/articles/inp)).

What you animate decides how much of the pipeline runs on each frame:

| Change | Stages re-run per frame | Examples | Thread |
|---|---|---|---|
| Geometry | Style → Layout → Paint → Composite | `width`, `height`, `top`, `left`, margins, font size | Main |
| Paint-only | Style → Paint → Composite | `color`, `background-image`/gradients, `box-shadow`, `border-radius`, SVG `d`/`r` | Main (raster can be off-thread, but the invalidation is main-thread) |
| Composite-only | Style → Composite | `transform`, `opacity` on a promoted layer; `filter` and `clip-path` on current engines | Compositor, survives a busy main thread |

The first three rows come from web.dev ([Rendering performance](https://web.dev/articles/rendering-performance)). The composite-only set has grown since the 2015 rule that only `transform` and `opacity` qualify ([web.dev, 2015](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count)). Chrome accelerates `opacity`, `filter` and `transform` by default, and from Chromium 89 it composites SVG animations and percentage transforms "as long as the layout size is not changing every frame" **[G]** ([Chrome, 2021](https://developer.chrome.com/blog/hardware-accelerated-animations)). Motion's 2025 tier list puts `clip-path` in its top tier as well, but Motion's own docs still describe `clip-path` and `background-color` as something Chrome "is adding." The sources conflict, and CSS Triggers is now out of date for these properties **[O]** ([Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list); [Motion docs](https://motion.dev/docs/performance)). The safe rule for the skill is this: `transform` and `opacity` are universal; `filter` and `clip-path` are composited on modern Chromium and Firefox but need a profile, with Safari checked separately **[I]**.

Getting onto the compositor is necessary but not sufficient. An element has to be promoted to its own layer, or even `transform` and `opacity` trigger paint. Composited animations can also **silently fall back** to the main thread: Safari's Core Animation does not support a `playbackRate` other than 1, and Chrome historically did not composite `%` translates **[O]** ([Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list)). JavaScript animation driven by `requestAnimationFrame` always runs on the main thread. That includes GSAP tweens, custom rAF loops, Lenis smooth scroll and WebGL shaders. WAAPI and CSS can hand composited properties to the compositor **[G]** ([Motion docs](https://motion.dev/docs/performance)). Motion itself sends transforms through WAAPI, so they "remain smooth, no matter how busy your main JS thread becomes," and it calls acceleration a progressive enhancement that "gets disabled" under conditions outside the developer's control **[V]** ([Motion docs](https://motion.dev/docs/performance)).

Layers have a price, paid in memory rather than time. A composited layer is stored as uncompressed RGBA at **4 bytes per pixel**, multiplied by DPR². Ten 800×600 photos with `will-change: transform` take about **19 MB**, and a single 3000×3000 element takes about **36 MB** **[C]** ([Smashing Magazine, 2016](https://www.smashingmagazine.com/2016/12/gpu-animation-doing-it-right/)). By the same formula, one full-bleed layer on a 390×844 CSS-pixel phone at 3× DPR is about **11.8 MB** **[C]**. Promotion is also contagious: elements stacked above a composited element get promoted too ("layer explosion"), and each upload from CPU to GPU costs about 3–5 ms **[O]** ([Smashing](https://www.smashingmagazine.com/2016/12/gpu-animation-doing-it-right/)). Hence web.dev's rule to promote nothing unnecessarily, and to apply `will-change` just before a change and remove it afterwards **[G]** ([web.dev](https://web.dev/articles/animations-guide)). The skill can price any effect with two numbers **[I]**:

- **Paint-bound effects** cost roughly painted area × effect complexity (for example, blur radius) on every frame.
- **Layer-bound effects** cost about width × height × 4 × DPR² bytes for as long as the layer lives.

A full-viewport backdrop blur on a 3× phone is the worst case on both counts.

The hard measurements behind all this are few and mostly old. In web.dev's demo, a `top`/`left` animation **dropped 50% of frames** and the `transform` version **1%** **[M]** ([web.dev](https://web.dev/articles/animations-guide)). Motion reports a site where one globally animated CSS variable forced style recalculation on **more than 1,300 elements, at about 8 ms per frame**: the entire 120 Hz budget, spent on elements that did not even use the variable **[M, vendor-reported]** ([Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list)). No 2024–2026 browser-vendor benchmark puts milliseconds on blur, shadow or gradient paint cost. That gap is a finding in itself. Most "never animate X" rules are deductions from the pipeline model, so the skill should verify with a profiler rather than recite them **[I]**.

## Ambitious UIs get slow by stacking, by thread contention and at load time

The first cause is **stacking**. Picture a backdrop-blurred sticky nav, a hover shadow that grows, an animated gradient hero and a scroll effect driven by a global CSS variable. Each is defensible alone, yet together they can exceed 8 ms at 120 Hz **[I]**, built from the per-effect costs in [Motion's tier list](https://motion.dev/blog/web-animation-performance-tier-list). The field data confirms this is common: **40% of mobile and 44% of desktop pages** ship non-composited animations, which force layout or paint **[M]** ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance)).

The second cause is **the wrong thread at the wrong time**. React re-renders "can easily take upwards of 100ms" against an 8–16 ms frame budget **[V]** ([Motion docs](https://motion.dev/docs/performance)), so routing per-frame values through `useState` cannot keep up. The worst long task in Trendyol's INP investigation was an IntersectionObserver callback that called React `setState` during scroll. That is exactly how most scroll-reveal components are built. Yielding with `setTimeout` or `scheduler.yield()` helped cut INP **50% from 963 ms** **[V]** ([web.dev Trendyol](https://web.dev/case-studies/trendyol-inp)). Preply found that interactions during hydration are slower on a Next.js app, which is when page-load animations also want the main thread **[V]** ([Preply](https://medium.com/preply-engineering/how-preply-improved-inp-on-a-next-js-application-without-react-server-components-and-app-router-491713149875)).

Smooth-scroll libraries take scrolling itself off the compositor. Lenis is driven by a per-frame `lenis.raf(time)` call in a requestAnimationFrame loop **[G]** ([Lenis README](https://cdn.jsdelivr.net/npm/lenis@1.3.23/README.md)), so any long task now stalls the scroll **[I]**. No benchmark of its cost exists. Usability evidence points the same way: NN/g found **all participants disoriented** on a fully scrolljacked page **[M, qualitative]** ([NN/g](https://www.nngroup.com/articles/scrolljacking-101/)).

The lab trend is not improving. Median mobile Total Blocking Time rose **58% in one year to 1,916 ms**. Only **63%** of the top 1,000 mobile sites pass INP, against 77% of all sites, so big rich sites do worse **[M]** ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance)).

The third cause, and the largest, is **loading**. The signature moves of design-led sites each damage a specific metric:

- **LCP.** Images are the LCP element on **76% of mobile pages**. About **16–17%** of pages lazy-load that image, an anti-pattern, and only about **17%** mark it `fetchpriority="high"` **[M]** ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance)). Preloaders and intro sequences push LCP past the loader by definition. No study isolates this effect, so it is an inference **[I]**.
- **CLS.** **62% of mobile pages** have at least one unsized image **[M]** ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance)). `font-display: swap` shifts layout when the web font replaces the fallback, unless the fallback's metrics are matched with `size-adjust` and the related overrides **[G]** ([Chrome](https://developer.chrome.com/blog/font-fallbacks)).
- **Page weight.** The median mobile home page is now **2,559 KB**, including 632 KB of JavaScript and 122 KB of fonts **[M]** ([Web Almanac 2025 Page Weight](https://almanac.httparchive.org/en/2025/page-weight)).
- **Home pages fail most.** They pass all three Core Web Vitals less often than secondary pages: **45% vs 56%** on mobile **[M]** ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance)). That is where design ambition concentrates.
- **Award-nominated sites.** The only measurement is a small 2022 lab study. betterup.com made **200+ requests to about 50 domains** on load and passed **12 MB** by the bottom of the page. Others made about 15–20 font requests or autoplayed a 1 MB video **[M, small sample]** ([Greenspector](http://greenspector.com/en/resources/blog/analysis_sites_nominated_mobile_excellence_awwwards/)).

The fourth cause is **testing on the wrong device**. A median phone (Moto G4) executes the same JavaScript **3–4× slower** than a Pixel 3, and a low-end Alcatel 1X more than **6×** slower **[M]** ([V8](https://v8.dev/blog/cost-of-javascript-2019)). DevTools says plainly that it "can't truly simulate the CPUs of mobile devices," and asks you to calibrate low-tier and mid-tier presets **[G]** ([Chrome DevTools](https://developer.chrome.com/docs/devtools/performance/reference)). Alex Russell's budgets assume a refurbished Galaxy A51-class phone (about $150) and test desktops of $350 or less **[O, data-backed]** ([Infrequently 2024](https://infrequently.org/2024/01/performance-inequality-gap-2024/)).

These four causes explain why the trade-off so often lands on "mediocre." The budget process, as written, gives three moves when a change breaches the budget: "optimize an existing feature or asset, remove an existing feature or asset, or not add the new one" **[G]** ([web.dev](https://web.dev/articles/performance-budgets-101)). When the cost is found after the design is finished, the effect was built on the expensive stage, and optimizing would mean rebuilding it. Removal is then the cheapest move. Teams that have been burned learn a blanket fear of motion. Agents trained on that code inherit both habits: the heavy defaults and the timid fallbacks **[I]**.

The stakes are real but directionally rather than precisely known. Deloitte's 37-brand study linked a **0.1 s** mobile speed gain to **+8.4%** retail conversions. Google commissioned it, and it is correlational **[V]** ([web.dev](https://web.dev/case-studies/milliseconds-make-millions)). Every web.dev case study is self-reported and survivorship-biased: Vodafone's +8% sales after a 31% LCP gain, for example, or Redbus's CLS dropping from 1.65 to 0 **[V]** ([web.dev](https://web.dev/case-studies/vitals-business-impact)). The better-controlled human-factors result is more pointed for a taste skill. In an 80-person shop study, **poor usability lowered perceived beauty after use**, while beauty did not raise perceived usability **[M]** ([Tuch et al. 2012](https://research.google/pubs/is-beautiful-really-usable-toward-understanding-the-relation-between-usability-aesthetics-and-affect-in-hci/)). Jank is not just slow; it makes the design look worse.

## Almost every costly effect has a cheap twin

The pattern behind nearly every fix is the same: **paint the expensive thing once, then animate the `opacity` or `transform` of the finished pixels**. The table below is the substitution list the skill should apply while it writes code, not after a profiler complains.

| Costly effect | Why it costs | Cheap twin | Grade |
|---|---|---|---|
| Animating `width`/`height`/`top`/`left` | Full pipeline each frame; cost scales with affected tree | FLIP: measure once, animate `transform`; isolate with `position: absolute` or `contain` | M (50% vs 1% drops), G ([web.dev](https://web.dev/articles/animations-guide); [Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| Reading layout between writes (`offsetWidth` inside a loop) | Forced synchronous layout ("thrashing") | Batch reads, then writes; one library per element | O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| Growing a `box-shadow` on hover | Repaints the blurred shadow every frame | Put the large shadow on `::after` at `opacity: 0`; animate only its `opacity` plus the element's `transform` | O, DevTools paint counts only ([Ahlin](https://tobiasahlin.com/blog/how-to-animate-box-shadow/)) |
| Animated gradient (`background-image`, `mask-image`) | Redraws a new gradient image each frame | Paint an oversized gradient once; `translate`/`scale` it, or cross-fade two layers | O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)), I |
| Large `filter: blur()` or `backdrop-filter` | Cost grows with radius and area; backdrop blur re-samples what is behind it as that content scrolls | Radius ≤10px (Perry's Framer warning), small surfaces only (a bar, not a sheet), a semi-opaque solid fallback, or a pre-blurred static image when the backdrop never changes | O, no benchmark exists ([Motion](https://motion.dev/blog/web-animation-performance-tier-list); [OpenReplay](https://blog.openreplay.com/creating-blurred-backgrounds-css-backdrop-filter/)) |
| Animating a global CSS variable | Invalidates style across the whole subtree; never accelerated, even when it feeds `transform` | Scope it to the element, register with `@property { inherits: false }`, or set the style directly from JS | M (1,300 elements, ~8 ms), G ([Motion](https://motion.dev/blog/web-animation-performance-tier-list); [Bramus](https://www.bram.us/2023/02/01/the-gotcha-with-property)) |
| Per-frame values in React state | A re-render per frame, at 100 ms+ each | `useMotionValue`/`useTransform`/refs, which write to the DOM with no re-render, batched to the next frame | V ([Motion](https://motion.dev/docs/react-motion-value)) |
| Scroll effects that read `scrollTop` in JS | One frame of lag, and main-thread work during scroll | CSS `animation-timeline: scroll()/view()`, or Motion `useScroll` passed straight to `opacity`/`transform`; `position: sticky` | G ([Chrome case study](https://developer.chrome.com/blog/scroll-animation-performance-case-study); [Motion useScroll](https://motion.dev/docs/react-use-scroll)) |
| Scroll reveal via IntersectionObserver plus `setState` | Long tasks during scroll (Trendyol's worst offender) | IntersectionObserver toggles a class; a CSS transition on `opacity`/`transform` does the rest; `unobserve` after the first reveal; yield any heavier work | V ([Trendyol](https://web.dev/case-studies/trendyol-inp)) |
| Smooth-scroll hijack (Lenis, Locomotive) | Scroll moves from the compositor to a rAF loop | Native scroll plus `scroll-behavior` and scroll-driven animations | G ([Lenis README](https://cdn.jsdelivr.net/npm/lenis@1.3.23/README.md)), I |
| `will-change`/`translateZ(0)` sprinkled everywhere | 4 B/px × DPR² per layer; implicit promotion of neighbours | Set it just before the change and remove it after; or paint small and `scale()` up (a 100× memory saving for soft content) | C, G ([Smashing](https://www.smashingmagazine.com/2016/12/gpu-animation-doing-it-right/); [web.dev](https://web.dev/articles/animations-guide)) |
| Long cloned marquees and tickers | Every composited animation is a layer | Fewer clones; pause off-screen with IntersectionObserver | O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| Animating SVG `d`, `cx`, `r` | Repaints every frame | `transform` on the SVG element or group | O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| View Transition morphs that change size | The default group animates `width`/`height` | Cross-fade plus transform; Bramus's technique strips the size keyframes | O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| Animated GIF | 3.7 MB for the example clip | `<video autoplay loop muted playsinline>` with WebM first: 341 KB WebM, 551 KB MP4 | M ([web.dev](https://web.dev/articles/replace-gifs-with-videos)) |
| Lottie for a spinner or checkmark | The classic runtime rasterises every path per frame on the main thread | CSS or SVG `transform`/`opacity`; keep Lottie for path morphing, lazy-loaded and destroyed off-screen (CPU fell from ~60–99% to ~27.5–90% in one rough test) | V ([LottieFiles](https://lottiefiles.com/blog/working-with-lottie-animations/hardware-accelerated-lottie-on-the-web-dotlottie-web-now-ships-webgl-webgpu)), M rough ([ICS Media](https://ics.media/en/entry/240625/)) |
| WebGL/three.js hero | ~185 KB gz, plus shaders that drop frames whenever the main thread blocks | A static poster as the LCP element; load the 3D lazily, only on capable devices, and pause it off-screen | M bytes ([bundlephobia](https://bundlephobia.com/api/size?package=three)), O ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)) |
| Large image decoded synchronously | One demo took 167 ms against a 16 ms budget; decoded size is 4 B/px whatever the file size | `decoding="async"`, `img.decode()` before revealing, and serve images at the rendered size | M secondary ([Dexecure](https://new-dexecure.netlify.com/blog/image-decoding/)) |
| Hero image lazy-loaded or unprioritized | Delays LCP | No `loading="lazy"` on it; add `fetchpriority="high"` (Google Flights' LCP went from 2.6 s to 1.9 s) | M, V ([web.dev](https://web.dev/articles/fetch-priority)) |
| Long below-the-fold sections | Layout and paint for content nobody sees yet | `content-visibility: auto` plus `contain-intrinsic-size: auto <estimate>` (232 ms → 30 ms in one demo) | M ([web.dev](https://web.dev/articles/content-visibility)) |
| Preloader or intro sequence | Holds back what LCP measures | No gate on first content; any intro animates content that is already painted | I |
| Several display families and weights | Bytes, plus swap-induced CLS | WOFF2 only, subsetted; preload just the LCP face; `optional` for body text, `swap` for display; metric-matched fallbacks (`next/font` does this automatically) | G ([web.dev fonts](https://web.dev/articles/font-best-practices); [Chrome](https://developer.chrome.com/blog/font-fallbacks)) |

Two cautions keep this table honest. First, a cheap twin is only cheap if it stays on the compositor. Motion's acceleration, Chrome's composited `filter` and the `clip-path` claims all come with "verify" attached, so the skill should profile under a calibrated low-tier CPU preset, not assume. Second, rAF libraries are not always the wrong answer. Motion's author concedes that rAF or GSAP can beat hardware acceleration when animating **thousands of small elements**, and that JS overhead itself "is rarely the bottleneck; expensive renders usually are" **[O]** ([Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list)). The rule is about what each frame touches, not about which library is used.

## The platform now does the expensive parts at 0 KB, but not all of it everywhere

The strongest shift since the classic guidance is that the premium effects agents reach for JS to build now exist as declarative platform features. They snapshot on the compositor, skip rendering, or run off the main thread. Readiness is uneven, so the skill should rank them and wrap the lower tiers in `@supports` or feature detection. | Motion `motion` component | 43 KB minimum **[V]**; whole package 59.1 KB gz **[M]** | As above | Avoid on the critical path; never ship both `motion` and `framer-motion` (73.5 KB gz) | [bundlephobia](https://bundlephobia.com/api/size?package=motion) |
| GSAP core | 27.4 KB gz, plus plugins; now free, including ScrollTrigger and SplitText | Main thread (rAF), with `lagSmoothing` to recover from spikes | Timelines, SVG morph, text splitting, very many elements; load per route | [bundlephobia](https://bundlephobia.com/api/size?package=gsap); [GSAP](https://gsap.com/pricing/); [GSAP 1.12](https://gsap.com/community/gsap-1-12-0) |
| Lenis | 5.5 KB gz | Main thread, and it owns scrolling | Rarely worth it: cheap in bytes, expensive in thread | [Lenis README](https://cdn.jsdelivr.net/npm/lenis@1.3.23/README.md) |
| lottie-web / dotlottie-web | 76.8 KB / 33.1 KB gz, plus WASM | Main thread (classic) or WebGL/WebGPU **[V]** | Illustrations that need path morphing; lazy-loaded | [LottieFiles](https://lottiefiles.com/blog/working-with-lottie-animations/hardware-accelerated-lottie-on-the-web-dotlottie-web-now-ships-webgl-webgpu) |
| three.js | 184.9 KB gz | Main thread (rAF) | A deliberate signature moment, gated by device and lazy-loaded | [bundlephobia](https://bundlephobia.com/api/size?package=three) |
| *For scale: Tailwind Play CDN* | 123 KB gz, render-blocking **[M-here]** | Main thread, compiling CSS at runtime | Never in production (see the next section) | [Tailwind](https://v3.tailwindcss.com/docs/installation/play-cdn) |

Bundlephobia figures are whole-package upper bounds, queried 2026-10-29. Head-to-head speed claims between libraries come from the vendors themselves. Motion's "2.5× faster than GSAP" from unknown start values and "6× faster" unit conversion are Motion's own benchmarks **[V]** ([Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list)). GreenSock's circa-2015 finding that CSS transforms used about 2× the CPU of its JS is a decade-old snippet the research could not open ([GreenSock forums](https://greensock.com/forums/tags/test/)). No independent low-end-Android benchmark of Motion vs GSAP vs CSS exists. The defensible comparison is structural **[I]**: WAAPI-backed animations can survive a busy main thread and rAF-backed ones cannot. That matters most during hydration and data fetching, which is when Next.js page-load animations run.

## The owner's portfolio: two loading costs to fix, and motion that is already cheap

The portfolio the owner chose in the blind B4 test ([experiments/results.md](../experiments/results.md); source at [b4/index.html](../experiments/runs/baseline/b4/index.html)) is a useful real case. It feels rich, yet almost all of that richness comes from type, layout and composited motion. I read the source and probed the page in Chrome 152 on a Mac (DPR 2, unthrottled). ## A build order, a budget and a lint that design performance in

### Build order: cost decisions happen before effects exist

The order matters because each step fixes which pipeline stage the next step can use. Retrofitting reverses it and forces deletions **[I]**.

| Step | What the agent does | Why here | Basis |
|---|---|---|---|
| 1. Static, styled, sized content | Real copy and real images; build-time CSS (never a runtime compiler); every `<img>` has `width`/`height`; LCP element chosen deliberately (image or headline) | LCP and CLS are decided here, and 62% of pages fail sizing | [Almanac](https://almanac.httparchive.org/en/2025/performance); [Tailwind](https://v3.tailwindcss.com/docs/installation/play-cdn) |
| 2. Loading discipline for the hero | LCP image in AVIF/WebP via `<picture>`/`srcset`, `fetchpriority="high"`, not lazy; ≤2 families, WOFF2 subsets, pinned axes, the LCP face preloaded, metric-matched fallbacks (`next/font` in Next.js) | The heaviest assets get prioritised before anything competes with them | [web.dev](https://web.dev/articles/fetch-priority); [web.dev fonts](https://web.dev/articles/font-best-practices); [Chrome](https://developer.chrome.com/blog/font-fallbacks) |
| 3. A cost plan for every effect | For each planned effect, write down its stage (composite, paint or layout), its thread, and its cheap twin from the substitution table; give the one signature moment its own line | Stops stacking before it starts | [Motion](https://motion.dev/blog/web-animation-performance-tier-list), I |
| 4. Platform motion | CSS transitions plus `@starting-style` for enter and exit; same-document View Transitions for state and route changes; `animation-timeline` inside `@supports`, with a static or IntersectionObserver class fallback; everything inside `prefers-reduced-motion: no-preference`, with a cross-fade as the reduced alternative | 0 KB, and on the compositor | [Chrome](https://developer.chrome.com/blog/entry-exit-animations); [Chrome VT](https://developer.chrome.com/blog/view-transitions-misconceptions) |
| 5. JS motion only where the platform cannot | Motion via `LazyMotion` + `m` with features loaded async, or GSAP per route; per-frame values in MotionValues or refs, never `setState`; IntersectionObserver callbacks only toggle classes | Keeps the critical bundle small and React out of the frame loop | [Motion](https://motion.dev/docs/react-reduce-bundle-size); [Trendyol](https://web.dev/case-studies/trendyol-inp) |
| 6. Gate the heavy experiences | WebGL, Lottie and video loops go behind a poster, `import()` on visibility or interaction, no reduced motion, no Save-Data, and a device tier (`hardwareConcurrency`; `deviceMemory` where present; unknown counts as mid-tier). The ≥4 thresholds are a common heuristic, not a sourced rule | A fast core for everyone; the extras only where they can run | [web.dev adaptive loading](https://web.dev/articles/adaptive-loading-cds-2019) |
| 7. Below-the-fold economy | `content-visibility: auto` on long sections; pause off-screen loops; `decoding="async"` | Cheap rendering for content nobody sees yet | [web.dev](https://web.dev/articles/content-visibility) |
| 8. Measure, then let taste spend the slack | Static lint, then a rendered probe with calibrated CPU throttling; use any leftover budget for the signature moment | Measured headroom, not optimism, decides how much to spend | [DevTools](https://developer.chrome.com/docs/devtools/performance/reference) |

## Conclusion

The "fast or beautiful" trade-off is mostly a sequencing error. Once a designer or agent knows which stage each effect costs, the menu of rich effects that stay cheap is long, and since 2025 most of it is native: compositor transforms, snapshot-based View Transitions, CSS-only enter and exit, scroll timelines and skipped off-screen rendering. The expensive part of an ambitious page is usually not its motion at all. It is what loads before anything moves: runtime compilers, font axes nobody asked for, unprioritised heroes, and libraries in the critical bundle. The owner's own page proves this on a small scale. A taste skill that equates restraint with speed would strip the parts he loved and keep the parts that cost him.

The implication for the skill is to treat performance as a **cost plan written before code**, enforced by a probe, not as a review afterwards. The evidence base is thinner than its confidence suggests. There is no modern benchmark of blur cost, no independent library comparison, and no Core Web Vitals study of award-winning sites. That makes this repo's probe the most credible measuring instrument the skill has. Logging LCP, long tasks, layer memory and font bytes for every blind-judged build would, within a few rounds, show whether the owner's preferences and the budget ever really conflict. The B4 evidence so far says they do not.
